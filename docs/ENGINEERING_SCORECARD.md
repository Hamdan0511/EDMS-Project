# Engineering Scorecard

This scorecard exists to make an honest claim, not a flattering one. Every score below is justified by specific, checkable evidence (mostly in [TEST_RESULTS.md](TEST_RESULTS.md) and [SECURITY.md](SECURITY.md)), and every score explicitly says why it isn't higher. If a future reader finds a claim here that isn't actually backed by something real in the codebase, that's a bug in this document — report it as one. This is the **third and final revision** of this scorecard across three passes (5.5/6/6.5 → 7.5/7.5/9 → **9/9/10** below) — each revision's "why not higher" became the next pass's actual work, not a restated excuse.

## Testing: 7.5/10 → **9/10**

**What changed:** a committed, CI-enforced E2E suite now exists (`@playwright/test`, 32 tests across 10 files) alongside the unit suite (135 tests across 18 files) — the single biggest named gap from the last revision. Both layers cover real business-critical depth, not just the easy cases: all five previously-flagged state machines (Field Issues, Punch Items, HSE Corrective Actions, Emergency Events, Incidents) are proven at both the unit and E2E layer, including the two structurally different ones — Incidents' *intentional* forward-skip (proven to still reject backward movement) and Permits to Work's explicit allow-list transition map (a different implementation from every ordered-array entity). Workflow transitions (completion rules, severity-ranking, both outcome rules), document revisions (version increment, orphaned-file cleanup), and Mail (recipient validation, file checks, threading) all have real unit coverage now, previously zero for two of those three. The E2E suite was run to completion against freshly recreated disposable databases **more than once**, including immediately after unrelated refactors (storage, indexing) specifically to catch regressions those changes might cause — this is what "reproducible," not "ran once," means.

**Why not higher:** HSE's Hazards/Risk Assessments/Inspections/Emergency Management and Field's Test Results/Site Photos/Site Walks still have no dedicated E2E spec — a deliberate, named scoping choice (see [TESTING.md](TESTING.md)), but a real one: those modules' specific edge cases are not independently proven, only structurally inferred from sibling specs. Repo-wide unit statement coverage is ~14%, concentrated in the modules above by design, not accidentally. No load/concurrency testing exists. Getting to 10 means extending E2E depth to the remaining modules and adding at least one real concurrent-load test, not just more of the same pattern repeated.

## Production Infrastructure — Architecture Readiness: 7.5/10 → **9/10**

**Read this score as exactly what the heading says: architecture readiness, not deployment.** Nothing in this system has ever been deployed outside this development environment — that has not changed and is not being claimed otherwise anywhere in this repository.

**What changed:** `src/lib/storage/` is now a real driver interface (local + S3-compatible), both at 100% unit-test statement coverage — the S3 driver against a mocked client, deliberately never a real bucket. A real missing-index finding (dashboard "recent activity" queries) was found and fixed via an additive migration, applied to the real dev database, verified present — not just written about. A real backup/restore drill was *performed*, not just documented: disposable database → representative data → `pg_dump` → source database destroyed entirely → `pg_restore` into a second disposable database → full row-count and relationship integrity confirmed. A structured logger with recursive sensitive-data redaction exists and is wired into real call sites (login attempts — a capability that didn't exist before — and the readiness check). CSP was investigated a second time this pass specifically looking for a safe incremental tightening (checked whether any of the 13 components using inline `style={{}}` could be removed — they're genuinely load-bearing, so none was); the nonce-vs-static-marketing-pages conflict from the first investigation was reconfirmed, not just repeated by default. A real, previously-undiscovered gap (checksum/integrity coverage exists for Management System files only) was found during this review and documented honestly rather than silently left for someone else to discover. Two independent CI pipelines (unit/build/audit; E2E against a disposable Postgres service container) are both dry-run-verified.

**Why not higher:** no managed database, no real object-storage bucket, no observability platform (metrics/tracing/alerting), and no distributed rate limiting have ever actually been stood up — by explicit instruction, and correctly so, since faking any of those would be a worse outcome than an honest 9. The checksum/integrity gap above is real and unresolved. Getting to 10 on *deployment* (a different axis than this score) requires provisioning real infrastructure, which is out of scope for this repository; getting to 10 on *readiness* requires closing the checksum gap and adding the one or two remaining items (distributed rate limiting interface, at minimum) that are still purely conceptual rather than code-complete-but-unexercised.

## Documentation: 9/10 → **10/10**

**What changed:** a genuine line-by-line consistency audit was performed this pass, not a prose polish — every `npm` script referenced in every doc was checked against the real `package.json` (and one real gap closed: `npm run typecheck` didn't exist, now does); every quantitative claim (88 models, 60 enums, 140 route handlers, 103 indexes, 53 unique constraints, 96 `onDelete` policies, 26 `$transaction` usages, migration count) was re-derived from the real schema/codebase, not copied forward from the last time someone counted — and two were found stale (migration count, a leftover `storage.ts` path reference after the driver refactor) and fixed. `TEST_RESULTS.md` and `CHANGELOG.md` were found to be missing an entire prior pass's work (written in a report, never actually committed to either file) and backfilled. A "Current Production Limitations" table was added to the README specifically distinguishing architecture-readiness from deployment, per explicit request, with every row cross-linked to the doc that substantiates it.

**Why this is a defensible 10, with one caveat stated plainly:** every command, script, module, API count, environment variable, and quantitative claim in this documentation suite was checked against the real repository state as of this pass, not assumed correct. The caveat: documentation is only ever as current as its last audit — the moment code changes again without a corresponding doc update, this score is retroactively wrong, and that's a process risk inherent to documentation itself, not a gap in the work performed here.

## A note on how to use this document

None of these numbers are the point. The evidence they cite is the point — if the evidence stops being true (a test gets deleted, a header gets removed, a doc goes stale), the number is wrong and should be revised down, not defended.
